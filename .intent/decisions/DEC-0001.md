## Context

All other work detail pages on the site use the shared `CaseStudy` component, which renders a fixed set of sections: problem, approach, what was built, what was hard, stack, outcomes. The component is designed for project retrospectives — narrative prose with bullet lists.

The Intent page needs a substantially different content model: code blocks with language labels, command reference tables with flag subrows, package cards, tool listings with signatures, and multi-IDE configuration examples. CaseStudy has no mechanism for any of this.

## Decision

Write `app/work/intent/page.js` as a self-contained custom page with its own local components (`CodeBlock`, `CommandRow`, `ToolRow`, `PackageCard`, etc.). These components are defined inline in the file — not extracted to shared components — because they are specific to this page and would add no reuse value elsewhere.

The page still uses the site's global CSS variables, layout classes (`.wrap`, `.cs-grid`, `.eyebrow`, `.display`, `.pill`, `.btn`), and the same two-column section grid pattern as CaseStudy. It reads like the rest of the site visually while having the structure its content actually needs.

## Consequences

- The Intent page cannot be data-driven via a `data` object passed to CaseStudy — it is a bespoke component
- Any future redesign of the site's section grid or typography tokens will need to be applied to this page separately
- The inline component definitions keep the file self-contained and easy to reason about, at the cost of some duplication with patterns used in other pages
